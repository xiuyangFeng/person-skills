# 全量同步审计（文档更新到最新）

触发：「同步文档 / 文档更新到最新 / 全量同步 / 文档对一遍 / 一致性检查」，或 [parallel-sessions.md](parallel-sessions.md) §6 的条件。
目标：所有**活文档**说的是现状，且彼此一致、能对上产物；快照保持原样；历史只补记不改写；不编造。

原则一句话：**先拿事实，再改文档；改活文档，不改快照；逐条核实，定点修改；只移动不删改。**

## 第 0 步：建事实表（不先动文档）

1. **事实源优先级**（高 → 低）：
   1. 运行产物：run 目录、完成标志（如训练日志里的完成行）、评估文件、队列状态文件（有无 finished / 失败记录）、发布包目录；
   2. 调度器 / 进程 / 服务：作业状态（运行中 / 结束 / 失败）、`ps` 启动时间、端口上实际进程、服务健康接口返回的版本；
   3. git：最近提交（代码、部署、数据工具），未提交改动；
   4. 跟踪文档里带日期的最新记录；
   5. 入口、总览、总纲等汇总文档；
   6. 记忆 / 口述。
   低一级的说法与高一级冲突时，以高一级为准。
2. 列出本次要核对的**跨文档事实**（以 profile `fact_registry` 或 `fact_registry_doc` 指向的登记表为底，补上本次新发现的）：数据版本、底座 / 基线及其数字、部署版本与在用模型、运行中与刚结束的作业、共享资源占用与预留、冻结目录 / 共享缓存及其依赖、节号上限、未决决策与用户最新裁定。
   每条写下「现值 + 来源（路径 / 命令 / 提交）+ 核查时间」。
3. **看并发**：`git status`、最近 3 小时改过的文档、调度器里其他作业；记下哪些文件别的会话正在动（这些文件只追加补记）。

## 第 1 步：分清活文档与快照

| 类别 | 例子 | 处理 |
| --- | --- | --- |
| 活文档 | 入口 README、各块 README 的「当前状态」、跟踪文档的状态头与最新节、总纲 / 路线图里的状态表、活待办表、规范里的操作说明、profile | 改到现状 |
| 快照 | 带日期的报告、汇报材料、历史卷、推进记录旧条目、跟踪里已结束的历史小节、决策记录原文 | 正文不改；必要时在其后加「后续状态（YYYY-MM-DD 补记）」 |
| 非 Markdown | 工作簿、图、HTML | 本次不改；需要时在汇报里列为待办 |

清单来源：profile 的 `live_docs` / `snapshot_patterns`；没有就按上表从 `doc_layers` 推断，并在汇报里提议补进 profile。

## 第 2 步：过时扫描

在活文档里搜两类东西，逐个对照第 0 步的事实表：

- **会衰减的状态词**：待确认 / 待裁定 / 未提交 / 已提交 / 运行中 / 训练中 / 在跑 / 排队 / 尚未 / 仍是 / 默认仍 / 暂不 / 未切换 / 未上线 / 计划 / 下一步 / 预计 / 约…完成；英文同理（pending / running / queued / TODO / will）。
- **会过期的标识**：旧版本名、旧包名、旧进程号 / 作业号、「目前用到 §N」这类计数、「当前状态（日期）」标题里的日期、旧数字（被新读数取代的指标）。

参考命令（路径与词表按 profile 调整）：

```bash
LIVE="<profile.live_docs 展开后的文件列表>"
grep -n -E "待确认|待裁定|未提交|已提交|运行中|训练中|在跑|排队|尚未|仍是|默认仍|未切换|未上线|预计|约.{0,12}完" $LIVE
grep -n -E "<旧版本名>|<旧包名>|<旧作业号或进程号>|目前用到 §|当前状态（" $LIVE
```

命中不等于过时：图例、历史变更记录、已带最终状态的历史叙述可以保留。

## 第 3 步：逐条核实（不推断）

| 文档说法 | 怎么核实 |
| --- | --- |
| 「预计 / 约 X 时完成」「运行中」 | 看完成标志、评估文件、队列状态文件；调度器里是否还在 |
| 「进程 / 服务 PID、版本」 | `ps -o lstart`、端口上的实际进程、健康接口返回的版本 |
| 「已上线 / 已合并 / 已推送」 | `git log` 与服务版本；发布目录是否存在 |
| 「已下线 / 已删除」 | 目录是否还在、是否已移到归档位置 |
| 某个读数 | 指回读数文件（metrics / readout）里的字段；不凭记忆抄 |
| 「X 已决定」 | 找到用户裁定的记录（跟踪里的裁定节或推进记录） |

- 找不到证据的说法不写成事实：写「未核实」，或问用户。
- 发现中断 / 失败照实写：停在哪（如第几轮）、何时、有无评估、与什么事件吻合（如节点停机）以及证据强度；要不要补跑交给用户。

## 第 4 步：安全编辑

- 定点替换（精确字符串 + 唯一性断言）；一次脚本改多处时，**先全部断言通过再写回**，避免改一半。
- 改前查新鲜度：别的会话 30 分钟内改过的文件，重读后再改，能追加就只追加。
- 顺序：先改事实的**规范位置**，再改镜像；镜像写一句话 + 链接。
- 过时的旧说法：要么改成现状，要么加前缀「（已由 YYYY-MM-DD 的 X 取代）」保留原文作历史——入口和状态块用前者，过程记录用后者。
- 新写入的说法注明来源与时间，例如「据 git 与进程信息 YYYY-MM-DD HH:MM 补记」。
- 每改一份文件，复核断言命中次数；改完 grep 一遍新文本确认落盘。

## 第 5 步：结构修复

常见的并发写坏：表格行跑到表格外、执行记录追加到了后面一节、同一节号重复、状态符号不在图例里、断链。

- 只移动不删改：移动前存副本，移动后对「排序后的行」做 diff，确认只有新增行、没有丢失行。
- 状态符号用文档图例里已有的；需要新符号就先改图例。
- 修完在汇报的「发现并改正的错误」里列出。

## 第 6 步：推进记录补缺

1. 用 `git log --since=<上次同步日期>` 与各跟踪最新节的日期，列出这段时间的事件（数据版本、重训、部署、暂停、重组……）。
2. 对照推进记录文首，缺的补**指针条目**（一两句 + 链接到跟踪节；见 [templates.md](templates.md) §指针条目），按日期插到正确位置（最新在上）。
3. 本次同步本身记一条（改了哪些、发现的错误）。

## 第 7 步：收尾与汇报

- 若 profile 或仓库登记表过时（路线状态、状态主文档路径、节号上限、登记表缺项）：一并更新。
- 记忆（若在用）里过时的项同步。
- 按 [templates.md](templates.md) §汇报 报告四组：**改了哪些文件**（分组）· **核查中发现并改正的错误** · **有意没改的**（快照、非 md、别人进行中的区域）· **需要用户决定的**。

## 附：这套做法为什么有效

- 事实表先行，避免「拿一份过时文档去更新另一份文档」的连锁错误。
- 活文档 / 快照二分，避免把历史改成「事后诸葛」，也避免在快照上浪费时间。
- 逐条核实会顺带抓出真正的问题（中断的作业、换了的服务进程、写坏的结构），这些往往比措辞过时更重要。
