# 多会话并行协议

适用场景：同一仓库里同时开着多个 AI 会话（不同工具、不同课题），每个会话只熟悉自己那块。
文档分叉几乎都来自三个缺口：**开工时不知道别人改了什么、占用共享资源不告诉别人、做完只改自己那块不传播跨文档事实**。
本协议把这三个缺口各补一步。所有路径与「规范位置」以 `PROJECT_PROFILE.md` 为准（`fact_registry` / `fact_registry_doc`、`shared_resources` / `shared_resources_doc`、`live_docs`）。
为了让不读 skill 的 AI（例如只读 `AGENTS.md` 的工具）也遵守，建议把本协议的摘要写进仓库：知识库规范里一节 + 根 `AGENTS.md` 几行指针 + `CLAUDE.md` 导入 `AGENTS.md` + Cursor 规则一条。

## 1. 开工检查（每个任务开始时，约 1 分钟）

1. 读 profile；读本任务所属块的 README「当前状态」和跟踪文档最新一节；读推进记录文首 3–5 条。
2. 读 `fact_registry` 里与本任务相关的事实的**规范位置**（不要从镜像处读现状——镜像可能已过时）。
3. 看谁在动什么：
   - `git status` / `git log -5`：有无别人未提交的改动、最近的提交（含部署、数据工具）；
   - 最近修改的文档：`find <docs_root> -name '*.md' -mmin -180 -not -path '*/_archive/*'`；
   - 调度器 / 后台进程 / 服务：`squeue -u <user>`（或等价）、`ps`、端口；共享计算节点的占用。
4. 发现文档说法和产物对不上（例如文档说「运行中」但作业已结束）：记下来，任务收尾时一并修；与本任务直接冲突就先告诉用户。

## 2. 跨线影响告知（占用共享资源或依赖别的线的产物时）

需要告知的情况：

- 占用别人可能也要用的计算资源（专用 GPU 节点、预留卡、长时间作业）；
- 新产物**依赖**另一条线的文件（链接到它的缓存、读它的中间结果）——对方清理或重建就会把你弄坏；
- 改动了别的线会读的共享文件（数据视图、统计、公共工具、配置模板）；
- 冻结了代码副本、或会让别人的队列指纹失配的改动。

做法：在**受影响的块** README（或 profile 指定的资源登记处）追加一条带日期的告知（模板见 [templates.md](templates.md) §跨线影响告知）：
谁（哪条线 / 哪一节）、从何时起、预计到何时、依赖或占用了什么、**对方不要做什么**、释放后如何确认。
只追加，不改对方的其他内容。资源释放、依赖解除后，在收尾同步里把告知改成「已释放（日期）」。

## 3. 收尾同步（任务完成、或阶段性停下时必做）

按顺序做，缺一步就是下一个会话的坑：

1. **本块跟踪**：结果 / 状态 / 作业号 / 证据路径写进跟踪文档对应节（节号按 profile 规则）。
2. **本块 README「当前状态」**：改成现状（日期写进标题），删掉被取代的「进行中 / 待裁定」说法（可保留一句「已被 X 取代」）。
3. **跨文档事实传播**：本任务改变了 `fact_registry` 里的哪条事实（数据版本、底座及数字、部署版本、运行中作业、共享资源、节号上限……）？
   - 先改该事实的**规范位置**；
   - 再按登记表逐个更新**镜像**（入口 README、总纲状态表、总览、待办表状态块等）；镜像只需一句话 + 链接，长内容不复制；
   - 登记表里没有、但你 grep 到别处也写了这条事实：同样更新，并在汇报里提议把它加进登记表。
4. **推进记录**：文首一条（完整条目或指针条目）。
5. **用户决定**：本轮用户的裁定（含「暂不做」「先不动」）写进相关状态处，注明日期与「用户决定」。
6. **撤销 / 更新跨线影响告知**；更新记忆（若在用）。
7. 汇报（[templates.md](templates.md) §汇报）。

> 判断要不要做第 3 步的捷径：把本任务的结论写成一句话，`grep -rn` 其中的关键标识（版本名、包名、作业号、节号、旧数字）在 `live_docs` 里出现在哪些文件——这些就是需要同步的镜像。

## 4. 编辑礼仪（防止会话之间互相覆盖）

- **定点替换**：每次改动用精确字符串 + 唯一性断言；不整文件重写，不顺手统一格式、重排段落。
- **改前看新鲜度**：文件在最近约 30 分钟内被改过（`stat` / `ls --time-style`）且不是你改的 → 先重新读最新内容再改；对方可能正在写，能只追加就只追加。
- **自己的块直接改，别人的块只补记**：对别的线负责的文档，只追加带日期的「补记 / 告知」，写明依据（「据 git log / 进程 / 产物 YYYY-MM-DD HH:MM 核查」）；不改它的实验内容与结论。
- **不回滚别人的改动**：认为别人写错了，先用产物核实；确实错了再改，并在补记里说明依据；拿不准就问用户。
- **历史内容只补记**：已结束的小节、决策记录、旧日志条目、带日期的报告不改正文，在其后加「后续状态（YYYY-MM-DD 补记）」。
- **新文件少开**：新事项优先续写所属块的跟踪文档；确需新文件时登记到块 README 的文件表。
- **渲染约束**：遵守 profile 的 `style.md_constraints`（例如某些渲染器不支持 HTML 注释或引用式链接）。

## 5. 冲突与分叉的处理

| 情况 | 处理 |
| --- | --- |
| 两份活文档对同一事实说法不同 | 以产物为准判断谁对；改错的那份；规范位置不明时按 `fact_registry` 补登 |
| 文档说已完成 / 运行中，产物显示中断 | 照实写「中断」：停在哪、何时、可能原因及证据强度；不自行补跑，要不要补交给用户 |
| 别的会话正在改同一文件 | 只追加；或等它改完（看 mtime）再做定点替换 |
| 文档结构被并发写坏（表格行跑到表外、条目落在错误的节） | 只移动不删改，移动后排序 diff 确认内容不变，在汇报里说明 |
| 事实变化来自另一会话、它没做收尾同步 | 你在收尾或全量同步时替它传播，补记里写「据 xx 核查补记」 |

## 6. 什么时候升级为全量同步审计

满足任一条就按 [sync-audit.md](sync-audit.md) 做一次：用户要求；连续几天多个会话并行后的节点（版本切换、部署切换、底座更换、数据版本更新）；开工检查发现入口与产物有 2 处以上对不上。
